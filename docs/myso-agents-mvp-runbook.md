# MySo Agents end-to-end MVP runbook

This runbook defines the first demoable vertical slice across MySo Core, Memory/MCP, Messaging, the AI-credit oracle, Automation and the MySo Agents web/Electron app. It is a deployment and owner-validation guide, not evidence that a service is running. The source tree is compile-checked; the owner performs all tests, service starts, wallet actions and transactions.

## MVP acceptance path

The initial demo uses a **named seller agent** because the current task contract creates offers for a buyer and a selected seller. It does not claim generic open-offer matching. Use separate buyer and seller agents, preferably controlled by two testnet wallets so both sides can approve and verify their own transitions.

1. Sign in to MySo Agents as the buyer, load the buyer agent's live identity, and confirm its on-chain task capability and MYSO spend policy. The app and work journal add no run-level, step-level, or gas spending cap; live on-chain capabilities, balances and action limits authorize spending.
2. Create a task offer for the named seller. The app creates an encrypted Messaging room, sends the private scope through it, submits the task offer with the room link, and verifies the finalized task and room-binding receipts. The authenticated MySo Agents API requires a room ID and checks the buyer agent's current fullnode `MessagingSender` membership before escrow submission; the protocol may still support roomless tasks created outside this demo.
3. Sign in as the seller, inspect the offer and authorized room history, accept the offer, and start the seller work run. Run only the planned actions; upload a deliverable to private Cloudflare R2 and verify its digest before `TaskDelivered`.
4. Return as the buyer, verify the artifact and finalized task history, then settle or use the dispute flow. Confirm the receipt reflects the same task, participants, amount and artifact digest.
5. Publish a seller-signed typed GraphManifest as a pinned MyData listing. The buyer verifies the seller signature, live listing quote, source-rights claims and live sell authority; completes a P2P purchase and grants the selected agent the proper reader access; then opens a graph page and runs a consented search. The purchase is an immutable graph-version snapshot. Do not enable series/latest-version behavior.
6. Configure an Automation job to dispatch the linked work run through the existing `action_worker`. Confirm that the worker has the selected live on-chain action capabilities and limits, a run-scoped credential, and the owner's standing graph/room/artifact consent. Verify progress, stop/cancel and receipt recovery before leaving it unattended.

The runnable MVP is blocked until its deployed contracts and service adapters match the source described below. Keep unavailable tools hidden or disabled; a green UI state is not proof of chain or storage readiness.

## Order to bring up and verify

1. **Pin a single testnet release set.** Record the Core package IDs/revision, Memory server and sidecar revision, Messaging relayer and SDK revision, oracle revision, MCP revision, app revision, pending migrations and required chain objects. Run the requested Core Move suite from the MySo social package only when the owner is ready; this agent does not execute it.
2. **Prepare chain and data services.** Deploy matching Core packages, configure live shared-object IDs and key servers, create the R2 bucket, apply Memory and Automation migrations, and enable only the MyData/task features used in the demo. Ensure test wallets and the acting agent own enough MYSO for the exact on-chain actions and gas; there is no application-side spend cap.
3. **Start dependencies in order.** Start Memory's database/cache, then Memory server and sidecar; Messaging relayer; AI-credit oracle; Automation database, sidecar and engine; finally the app. The app's `desktop:dev` command owns its loopback bridge; do not pair an arbitrary Next dev server with Electron sign-in.
4. **Prove identities before the demo.** Sign in on web and desktop, verify the MCP token audience and claims, load the same owner/account/agent/network from the live services, and confirm the custody vault can mint a caller-bound MyData session. Check that task and room tools appear only when current scopes, capabilities and service flags permit them.
5. **Run the six acceptance steps above with two wallets.** Save task, room, upload, purchase, graph-version and automation receipt IDs. Confirm finality and exact event/object/byte correlations at each boundary. Owner-wallet actions require the explicit wallet flow; agent-funded actions rely on current on-chain authority. Do not use an indexed preview as a finalized receipt.
6. **Exercise recovery before calling the MVP demo-ready.** Interrupt one run before dispatch and one after a submitted side effect; confirm pre-dispatch work can resume, ambiguous effects stay held, and only action-specific receipts release them. Pause/cancel an automation and verify already-dispatched effects remain visible. Revoke graph access and confirm the current Knowledge view clears and future key release is denied.

## Current source gaps and owner-run gates

- The app has the named-seller task flow, encrypted room coordination, delivery packaging/R2 integration, task history, settlement/dispute UI, graph publication/purchase/read flow, and durable Automation dispatch in source. Those pieces are not yet a verified deployed end-to-end run.
- Bounded MyData purchase, post-access purchase, graph key release, graph decryption and owner checkout are default-off or deployment-gated. Apply the matching Move package and explicitly configure the corresponding Memory flags only after validating the live key-server policy.
- Hosted MCP has principal-bound journal dispatch in source; a configured endpoint alone is insufficient unless the deployed MCP server uses that build and the app's custody client supplies the live short-lived MyData session on journal calls.
- Task offers are currently named-seller offers. Generic open-offer acceptance needs a task protocol change and is outside this first demo path.
- Durable work-run dispatch and bounded asynchronous continuation are implemented in source. Orphan automation runs can be reconciled without replay, and uncertain action outcomes remain held until receipt-backed recovery. Deployment/migrations and owner validation of credential expiry/revocation, process restarts, linked-delivery recovery, and exhausted retries remain open; stop at this gate if an action can be duplicated or its result cannot be proven.
- Web and desktop identity, OAuth issuer registration, app callback URLs, R2 credentials, deployed key-server quorum, model-provider retention and testnet service availability are environment-specific and cannot be established by source compilation.

# Current catalog action coverage — MySo Agents

For PoC transfers, `poc_get_beneficiary_transfer_receipt` verifies recipient acceptance against the account/agent-prepared digest, configured package, recipient signer, exact beneficiary ID, unique native acceptance event and successful checkpoint. `poc_get_beneficiary_transfer_proposal_receipt` independently verifies the oracle proposal using an identity/wallet-scoped job, live `PoCConfig` oracle authority and the exact finalized proposal event. Neither receipt substitutes for the other stage; the recipient acceptance flow is available in the web/desktop app and requires the proposed recipient wallet to sign before the beneficiary becomes claimable.

The production action catalog is now version 1.33.0: 113 of 114 on-chain actions have executable dedicated or generic approved-action routes; `bridge.initiate_transfer.v1` is owner-deferred. Protocol multisig setup is correctly modeled as the read-only `account_configure_multisig` descriptor utility, not as a chain action: the web/desktop owner-migration setup now checks the MCP descriptor against the wallet-key-derived local descriptor before using it. Organization treasury access, funding and withdrawal plus PlatformAdminCap developer transfer and task-market fee-recipient changes are wired through Move, SDK/PTB, server validation, MCP, receipts and owner/admin-wallet flows in the shared web/desktop app. They are compile-checked source paths; deployment/runtime verification remains open. The app and MCP now bind either the organization owner or a selected live group administrator as signer; server preparation rechecks current admin permission and Move rechecks it at execution. The PoC transfer has start/status/propose/job/proposal-receipt MCP tools plus the separate recipient wallet acceptance UI, action and finalized receipt. The deployment-gated bridge binds the wallet to verified MySo agent context, uses a dedicated server-to-oracle secret distinct from the identity-service secret, and validates the finalized proposal event against the current configured oracle. Source/compile evidence does not establish deployed service credentials or runtime behavior.

**113 of 114 current on-chain catalog actions have executable dedicated or generic approved-action routes; bridge MCP is owner-deferred.** Protocol multisig setup is exposed separately as `account_configure_multisig`; no fake Move action is advertised. Profile tipping and on-chain storage-capacity purchases are excluded from the production catalog; tipping is post-only and task artifacts use Cloudflare R2. This includes the new seller `mydata_publish_graph` path plus 41 generated task/jury tools, verified task-room binding, bounded direct MyData and post-bound purchases, owner-agent, subscription, payment, creator-vault, spot-market, governance and object-transfer actions, SPT buy/sell actions with exact-input PTBs and finalized receipt readers, and a recipient-wallet acceptance UI for verified PoC beneficiary transfers. SPT buys use agent-owned MYSO coins under the live per-action cap; eligible bounded MyData and post-access purchases also use the agent’s MYSO under live on-chain capability/approval policy and per-action limits. There is no seller allowlist or app-side spending cap; owner signatures remain required when the on-chain action policy requires approval. Creator-fee escrow payouts are settled atomically in the trade PTB. `spt_get_trade_quote` now reads live pool/config objects and returns Move-matched curve/fee output plus each nonzero escrow beneficiary; `poc_get_vault_for_beneficiary` resolves the indexed vault candidate. The quote is indicative, and deployment plus owner-run execution verification remain open. Owner actions create exact-input approval intents; signatures and native ownership checks remain required. Post-bound purchase requires `MYDATA_POST_ACCESS_PURCHASE_ENABLED` and the upgraded Move package; it is default-off. Token transfers, profile subscriptions, creator-vault claims, spot-market creation, spot-payout claims, spot betting and SPT trading are disabled by default pending deployment configuration. Five owner-agent policy actions have dedicated approval-request tools, with owner signatures and a default-off deployment gate. `assets_list_owned_objects` supplies bounded fullnode inventory; the owner-migration area now exposes a separate explicit object-transfer list with one owner approval and wallet signature per selected object, restart-safe operation metadata and a scoped finalized object-change receipt matching ID, exact Move type and recipient; these transfers are separate from the atomic registered-reference migration. Read-only graph offer discovery remains a seller-proof-unverified metadata preview until the caller explicitly runs verification; purchase controls require verified seller proof and a live exact quote. Existing MCP reads cover rooms, work runs, task-market records and participant-scoped task history, automation deliveries, organization audit records and chain receipts. Fixed-path MCP read facades cover the current social-server SPT/reservation-pool and public creator-vault read endpoints; remaining read work is still a field-by-field inventory across the rest of the APIs. Private MySocial typed JSON graph search is exposed as `mydata_search_graph`, targeted node/edge/evidence reads as `mydata_get_graph_item`. The publisher validates and signs a typed GraphManifest, binds graph ID/version into publication capsule v2, checks current seller authority, records the exact encrypted digest and tag hash, and submits an existing listing action. Each finalized graph purchase now emits an immutable graph ID/version, manifest hash and seller-signature digest snapshot, shown after fullnode receipt verification. `series_stream` is rejected because the owner selected immutable per-purchase snapshots; subscriptions extend only the same pinned listing, while later versions need separate purchases. Buyer lifecycle/revocation propagation, derived-data retention controls, the broader field-by-field read inventory and deployment/runtime validation remain open.

Room membership administration is outside the social action-catalog denominator. MCP `messaging_add_room_members` grants reader and sender permissions only after live `MessagingReader` and `ExtensionPermissionsAdmin` checks, and reports success only after finalized fullnode permissions are re-read. Its disclosure states that new readers can decrypt existing and future history. The web/desktop panel requires an explicit confirmation before submitting the same grant. Custom MCP `messaging_revoke_member_from_all_rooms` provides a preview/execute flow for one target: execute requires both `messaging:read` and `messaging:write`, repeats a complete room scan capped at 500 indexed rooms, compares the exact confirmed room IDs, then rechecks membership and verifies each individual finalized remove-and-key-rotation receipt. It is unavailable to unattended worker credentials and hosted coordinator runs; partial/uncertain outcomes stop without automatic retry. The authenticated reverse-membership index can lag, so this cannot prove a global room inventory. Source/typecheck evidence only; no runtime or chain action was performed.

A source-level inventory compared every literal `social_*` resource dispatched by `services/server/src/platform_reads.rs` with the `/api/agent/read/social_*` resources registered by `packages/mcp/src/platform-tools.ts`; no literal social-reader resource is missing an MCP route. The social reader now also exposes the core two-way relationship check as `social_check_follow_relationship`, with both wallet IDs normalized and validated before the fixed upstream route is called. This verifies route-name coverage only. Parameter parity, authenticated scope and organization-role enforcement still require a field-by-field audit, as do non-social task, room, organization, automation and receipt lists.
